# Onlyfarms / AgroPulse — инструкции по ветке интерфейса

Эта ветка: `J-D/frontend-handoff-dec04-2026`. Основной продукт — `/scouting`.
Начни с [досье разработчика](docs/frontend/README.md). Оно описывает **именно эту
ветку**, а не состояние локального сервера автора или модельной ветки.

## Рабочая область

- Для UX/UI меняй `web/scouting/`, профильные тесты и документацию.
- В текущем приложении vanilla HTML/CSS/JS + Leaflet, Python stdlib HTTP и SQLite.
  Node нужен для JS-проверок, обязательного npm/build-процесса нет.
- Не заменяй стек ради небольшого улучшения. Если задача явно включает миграцию,
  сохрани API, геометрию и сценарии; сначала сделай один проверяемый вертикальный срез.
- Модельные исследования живут в `J-D/model-pilot-dec04-2026`. Не запускай обучение,
  сбор архивов, планировщики и массовые исследования для задачи оформления.
- Не переписывай `models/`, научные `data/`, пороги, маски, шкалы растров или метки
  ради красивого экрана. Версии и байтовые хеши имеют значение.
- Требуемое изменение API реализуй как отдельное согласованное по контракту изменение,
  с серверными проверками и тестами. Не маскируй его под изменение стилей.

## Смысл, который нужно сохранить

1. Карта → выбранная пара снимков → явное место 60 × 60 м → вопрос/задача →
   история того же места → отдельная запись настоящего осмотра.
2. R01–R27 — приблизительные обводки со скриншота, не подтверждённые номера полей.
3. NDVI/NDMI описывают спутниковый сигнал. NDMI не является датчиком влажности почвы.
4. Отсутствие пригодных данных — отдельное состояние, не нулевое изменение.
   Покрытие пикселями не является процентом точности модели.
5. Наблюдаемое изменение, прогноз будущего индекса, задача и фактический осмотр —
   разные сущности. Архив не переименовывать в актуальную тревогу.
6. Не создавать вымышленные посещения, фото, диагнозы, культуры, проценты вероятности,
   подтверждённые границы и экономический эффект. Форму результата можно показать в preview.
7. Новые функции модели могут отсутствовать здесь. Проверяй
   [матрицу веток](docs/frontend/BRANCH_STATUS.md); отсутствие API нельзя скрывать макетом ответа.

## Технические инварианты

- Не убирать Host/Origin/CSP и `X-Field-Token`, не включать wildcard CORS.
- Соблюдать `request_id` и идемпотентность: повтор прежнего тела — тот же ID;
  другое тело с прежним ID не является разрешением перезаписать событие.
- Не вычислять спутниковые/географические показатели повторно в браузере.
- Не менять растр CSS-фильтрами и не обрезать его так, чтобы координаты клика
  перестали совпадать с изображением. Пара дат и версия основания следуют за задачей.
- Черновик, местоположение, выбранная площадь и история должны сохранять связь.
  Старый асинхронный ответ не должен попадать под новый выбор пользователя.
- Пустой журнал при первом запуске — правильное состояние.

## Агентный процесс

Главная сессия координирует: `of-ux` и `of-contract` исследуют независимо,
`of-frontend` — единственный автор пересекающихся UI-файлов, `of-qa` проверяет результат.
Роли находятся в `.claude/agents/`; порядок и готовые запросы —
[AGENT_WORKFLOW.md](docs/frontend/AGENT_WORKFLOW.md).
Параллельные чтения полезны; параллельные записи в один файл — нет.
Нет необходимости запускать всю команду для исправления одной подписи.

## Запуск и проверка

На Windows с Python 3.13 x64:

```powershell
.\START_SCOUTING.cmd --port 8776 --directory data/frontend-dev-journal
```

Не использовать рабочий журнал хозяйства для технических проверок. Подготовка
окружения и независимые команды описаны в [SETUP_AND_TROUBLESHOOTING.md](docs/frontend/SETUP_AND_TROUBLESHOOTING.md).
Проверяй ровно затронутые сценарии и подходящие тесты, затем визуально desktop/mobile.
Не выдавай инженерные тесты за валидацию модели или тестирование агрономом.
