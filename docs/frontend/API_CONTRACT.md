# Реализованный контракт `/scouting`

Проверено 10 ноября 2026 по коду ветки `J-D/frontend-handoff-dec04-2026`, базовый
коммит `f2e1f29e873c74f4fba9dd498b441b9033316873`. Это описание работающего API
этой ветки, а не проект нового модельного сервиса. Чтение архива не выполняет
обучение, не вызывает внешние сервисы и не создаёт записи агронома.

Исходники: [сервер](../../agro_checker/scouting_server.py),
[архив, задачи, посещения](../../agro_checker/farm_scouting.py),
[общая пара и планы](../../agro_checker/farm_workspace.py),
[хранилище](../../agro_checker/field_store.py),
[фото](../../agro_checker/land_inspections.py),
[клиент](../../web/scouting/app.js), [клиент плана](../../web/scouting/plans.js).

## Маршруты

Все пути относительны адресу приложения. Ответ JSON, если ниже не указан PNG/фото.
Все перечисленные ключи query обязательны, кроме явно описанных вариантов.

| Метод и путь | Query / тело | Результат |
|---|---|---|
| `GET /api/scouting/state` | Без query | Обзор + задачи + посещения + планы + токен записи |
| `GET /api/scouting/workspace` | `period`; или `period,before,after` вместе | Общая пара, сводки всех площадей, доступные сцены |
| `GET /api/scouting/area` | `fid,period,before,after` | Детали площади именно на этой паре; `pair:null` при недостатке данных |
| `GET /api/scouting/detail` | `fid,period`; или `fid,period,before,after` | Низкоуровневые детали/индивидуальная пара; для рабочего сценария предпочесть `/area` |
| `GET /api/scouting/map` | `fid,period,before,after,key,side` | PNG; `key=ndvi\|ndmi`, `side=before\|after\|delta` |
| `GET /api/scouting/location` | `fid,period,before,after,relative` | `{location,comparison}`; сервер проверяет клик и назначает канонический `place.id` |
| `GET /api/scouting/history` | `place_id` | История NDVI/NDMI одного окна 60 м, включая пропуски |
| `GET /api/scouting/export` | Без query | Задачи и посещения, без токена и без списка планов |
| `GET /api/scouting/plans/export` | `id` | `{schema,plan,tasks,visits,automatic_diagnoses,model_training_enabled,notice}` |
| `GET /api/scouting/visits/{visit_id}/photos/{photo_id}` | Без query | Проверенные исходные байты фото и MIME |
| `POST /api/scouting/tasks` | JSON задачи ниже | Сохранённый event, а не объект `task` в дополнительной оболочке |
| `POST /api/scouting/visits` | JSON фактического посещения ниже | Сохранённый event |
| `POST /api/scouting/plans` | JSON плана ниже | Сохранённый event |

Нет отдельных `GET /tasks`, `GET /plans`, `PUT/PATCH/DELETE` задач или посещений.
Перечни читаются из `/state`, планы — из `state.plans`. Функций удаления/изменения
сохранённых событий UI обещать не должен. Повторное посещение — новая запись.

**В этой ветке отсутствуют:** `/api/scouting/review`, `/api/model/v1/inspection-priorities`,
эндпоинты Sentinel-1, свежих прогнозов и автоматической постановки задач.
Нельзя подставлять для них статический JSON и подписывать как работающую модель.
Карточка `/review` и будущий эксперимент находятся отдельно в модельной ветке;
перед интеграцией нужно согласовать их перенос и фактические схемы.

## Строгие query и статические страницы

- Сервер отвергает неизвестные/повторные ключи query и значения длиннее 120 символов.
  Разбирается не больше шести полей; не добавлять `cacheBust`, `design` или аналитику к API.
- Для явной пары передаются **обе** строки `before`/`after`, полученные из каталога сцен.
  Одна дата, другая эпоха, обратный порядок или одинаковые даты недопустимы.
- `GET /`, `/scouting`, `/scouting/about` принимают только необязательный одиночный
  `design=atlas|hightech`. У остальных static-ресурсов query не поддерживается.
- Названия ресурсов в явном allowlist сервера. Новый JS/CSS-файл нельзя просто
  положить на диск и ожидать, что сервер автоматически начнёт его раздавать.
- SPA-переходы `#map`, `#changes`, `#task`, `#history`, `#plan` и их параметры
  обрабатывает браузер. Это hash-маршруты, а не новые серверные HTML-пути.

## Ответы чтения и nullable поля

`/state` объединяет:

```text
items[]: {id, working_band_m, core_supported, core_area_ha, availability}
periods[]: параметры периодов из зафиксированного архива
snapshot_at: время создания протокола архива; не «погода сейчас»
version: SHA256 summary.json
confirmed_boundaries: false
automatic_diagnoses: false
model_training_enabled: false
tasks[], visits[], plans[]: сохранённые события журнала
diagnoses_enabled: false
training_enabled: false
token: текущий локальный токен сохранения
```

`/workspace` содержит `period,scenes,default,selection_rule` и при найденной паре:
`pair:{before,after,days}`, `rows[]`, `available_areas,total_areas,kind,version`.
Каждая сцена: `{id,at,baseline,usable_areas}`. Каждая строка площади:
`{id,status,reason,coverage,ndvi,ndmi}`; `status=ready|missing`.

Общая пара выбирается сервером только по датам/пригодности: поздняя сцена с ≥70%
индивидуально пригодных площадей, та же processing baseline, ранняя за 7–21 день,
ближе всего к 14 дням. По величине снижения пара не подбирается. Если подходящей
пары нет, ответ может быть `pair:null,rows:[],available_areas:0`; не вычислять свою
«удобную» пару на клиенте и не выдавать её за общую.

`/area` содержит `fragment,period,dates,working_band_m,height_m,core_supported,pair`.
У пригодной пары присутствуют `default_location,default_place_comparison`.
Если данных не хватает, `pair:null,default_place_comparison:null` и текст
`unavailable_reason`. Отдельные ранее вычисленные вспомогательные поля не означают,
что эту пару можно использовать: главный признак доступности — `pair`.

У `pair` есть:

- `before/after:{id,at,baseline}`, `days,same_baseline,coverage,paired_cells`;
- `metrics.ndvi/ndmi`: сводка `base`, значения `before/after`, сценарии чувствительности
  и серверный `robust`; полный набор возвращает научная функция `metric`;
- `crop:{west,north,width,height,cell_m}` — геометрия растра в UTM, не CSS-пикселях;
- `version,contours_sha256,source_hashes,selection` — происхождение основания.

Полные поля одного `metrics[key]` в этой ветке:
`base,shift_min,shift_max,all_shifts_available,shift_stable,core,outer,
all_scenario_min,all_scenario_max,tolerance,robust,core_supported,before,after`.
Числовые поля сценариев могут быть `null`; флаги не заменяют сами значения.

Значение `base` — медиана попиксельных разностей на общей пригодной маске. Оно
может отличаться от `after-before`, то есть разности двух медиан. Пересчитывать
`base` из двух отображаемых чисел нельзя. `coverage` — покрытие, не точность модели;
`robust` — результат сценариев границ, не статистическая вероятность.

`/detail` самостоятельно не блокирует все случаи разных baseline так же, как
обёртка `/area`: не использовать низкоуровневый маршрут для обхода проверки пары.

Ответ `/history`:

```text
{place_id, cell_m:60, total_cells, policy,
 rows:[{at,period,scene,baseline,ndvi,ndmi,coverage}, ...]}
```

Индексы/изменения могут быть `null`. Показывать отсутствие данных, не 0 и не
«состояние нормальное». Между пропусками не рисовать непрерывную линию. Разные
версии обработки явно различать. `default_place_comparison` и `/location.comparison`
имеют `{paired_cells,total_cells,coverage,ndvi,ndmi}`; для окна минимум 5 общих
пригодных ячеек и 80% покрытия. Пригодность площади не гарантирует пригодность окна.

## Координаты и идентичность места

`relative` в query `/location` — JSON-массив `[x,y]`, сериализованный через
`URLSearchParams`: оба числа в `[0,1]`, начало в **левом верхнем** углу PNG.
Это не latitude/longitude. Координаты клика вычисляются относительно фактически
отображённого изображения, с учётом рамки/letterbox и режима разделителя.

Сервер переводит клик через `crop` в UTM EPSG:32637, проверяет попадание в
приблизительную обводку и возвращает фиксированную 60-метровую ячейку.
`place.id` имеет вид `Rxx-{utm_cell_x}-{utm_cell_y}`. Ячейка привязана к глобальной
сетке; её опорная точка — representative point пересечения с обводкой. Это **не
измеренный GPS** и не обязательно ровно место, куда попал курсор.

Не конструировать `place.id` или округлённый lat/lon на клиенте. Повторные задачи и
посещения связываются по каноническому `payload.place.id`, не только по R-коду.
У самого окна на краю может быть меньше девяти целиком содержащихся 20-м ячеек.

## POST задачи: построение тела без фиктивных данных

Пример ниже только строит тело из текущего серверного ответа и полей пользователя;
он ничего не отправляет и не является сохранённой задачей.

```js
function taskBody({requestId, detail, metric, relative, actor, plannedDate, objective}) {
  const p = detail.pair; // из /area, именно текущая явно выбранная пара
  if (!p) throw new Error('Нет пригодной пары');
  return {
    request_id: requestId, fragment: detail.fragment, period: detail.period,
    before: p.before.id, after: p.after.id, version: p.version,
    relative, actor, planned_date: plannedDate, objective, metric
  };
}
```

Все 11 ключей обязательны, лишние ключи отвергаются. `relative:null` означает
серверную опорную точку, массив — выбор человека. **UI сначала требует явного
подтверждения места**: сам бэкенд отдельного `location_confirmed` в теле не имеет.
`metric=ndvi|ndmi`; `actor` — непустая строка до 120 символов; `objective` —
непустая строка до 2000. `planned_date` — `""` либо дата `YYYY-MM-DD` с 2000 года;
`null` не является пустой датой. Старая `version` отвергается: обновить чтение и
снова подтвердить выбор, а не заменять хеш в старом теле незаметно для пользователя.

Сервер сам прикладывает `place,evidence,place_evidence`, цель
`human_task_from_archive_not_current_alert`, период и `confirmed_boundary:false`.
Нельзя присылать собственные индексы/качество в задаче. Задача не становится посещением.

## POST посещения: только фактический ввод человека

Точная структура:

```text
{
 request_id: строка 32 lowercase hex,
 task_id: id существующего сохранённого события задачи,
 actor: непустая строка до 120,
 observed_at: ISO 8601 со смещением часового пояса или Z,
 notes: непустая строка до 10000,
 outcome: observed_change | nothing_notable | unclear | not_checked,
 follow_up: строка до 2000, допускается "",
 photos: [{filename, data_base64}, ...], допускается [],
 real_visit_confirmed: boolean из явно отмеченного подтверждения человека
}
```

Все 9 ключей обязательны, лишние отвергаются. Сохранение возможно только при
`real_visit_confirmed===true`. Дата не может быть в будущем или раньше 2000 года.
Клиент существующей ветки собирает московское время как `...:00+03:00`; при
другом UX таймзона должна оставаться явной, а не зависеть от настроек ноутбука.

`outcome` — ответ человека, не автоматическая диагностическая метка. Сервер
возвращает `observation_source:manual_unverified_report`. Время раньше создания
задачи допускается, но отмечается `retrospective_entry:true`. Фото, дата и GPS
самостоятельно не удостоверяются. Просмотр пустой формы или предпросмотр результата
не должен отправлять POST и не должен автоматически отмечать реальный визит.

### Фото

- До 3 фото, каждое 1–5 000 000 исходных байт. В теле — **чистый base64**, без
  префикса `data:image/...;base64,`. MIME отдельно в POST не присылается.
- JPEG/PNG/WebP, один кадр, до 32 000 000 пикселей и максимум 12000 по стороне.
  Сервер проверяет декодирование и действительный формат, а не расширение файла.
- `filename`: 1–200 символов, без управляющих символов; отображать как текст.
- Одинаковые по байтам фото в одном посещении отвергаются. ID фото — SHA256
  исходных байтов. Хранится оригинал, не подтверждение EXIF-времени/GPS.
- Ответная метаинформация: `id,sha256,mime,bytes,width,height,original_name,
  photograph_time_or_gps_verified:false`. Байты лежат отдельно в журнале.
- URL просмотра строится по **ID события посещения** и **ID его фото**, не по
  `task_id`. Фотография, не прикреплённая к этому посещению, недоступна по маршруту.
- Черновики посещения и File-объекты остаются в памяти вкладки; не переносить их
  в Git, localStorage/sessionStorage, фиктивные fixtures рабочего журнала.

## POST плана

Ровно `{request_id,title,task_ids,purpose}`. `title` непустой, до 160 символов.
`purpose=inspection|sensor_survey`. `task_ids` — массив ID **уже сохранённых задач**,
1–3 уникальных задачи и 1–3 разных `place.id`. Две задачи одного места в одном
плане не допускаются. Порядок массива сохраняется, оптимизации дорожного маршрута нет.

Payload фиксирует `task_sha256` оснований и получает `status:planned_not_visited`,
`route_optimized:false`, `confirmed_boundaries:false`. Для `sensor_survey` сервер
добавляет вопросы об условиях размещения; это не установка/показания датчика.
Печать, скачивание GeoJSON и локального HTML выполняет `plans.js`, отдельных
серверных маршрутов для них нет. Экспорт плана проверяет хеши задач и возвращает
посещения тех же мест, включая записи по другим задачам этого места.

## Событие, идемпотентность и локальное хранение

Каждый успешный POST возвращает:

```text
{id,kind,profile_id,recorded_at_utc,payload,sha256}
```

`id` — 32 hex, `sha256` — SHA256 канонического JSON payload, `profile_id` —
технический поток `farm-scouting-01`. `kind` равен `farm_scouting_task`,
`farm_scouting_visit` или `farm_scouting_plan`. `recorded_at_utc` — время записи
сервера; дата осмотра отдельно в `payload.observed_at_utc`.

Все payload дополнены `request_id,request_sha256,schema_version:1,
automatic_diagnosis:null,model_training_eligible:false,forecast_scoring_eligible:false`.
Эти поля не означают наличие обученной модели осмотров.

`request_id` — `crypto.randomUUID().replaceAll('-', '')`, отдельный стабильный ID
конкретной формы. Повтор **того же тела** с тем же ID возвращает прежнее событие.
Изменённое тело с тем же ID отвергается; для нового действия нужен новый ID.
Проверки входа/архива выполняются перед поиском повторного события: устаревший архив
или теперь некорректные даты могут помешать и повтору. Не генерировать ID на каждый
сетевой retry и не мутировать тело уже отправленного неопределённого запроса.

SQLite: `<directory>/field.sqlite3`, таблица `events`, append-only триггеры запрещают
UPDATE/DELETE. Фото: `<directory>/farm-scouting-media/{sha256}.bin`. При переносе
журнала нужны БД **и папка фото**. Хеши проверяются при чтении; это локальная
целостность, не внешняя цифровая подпись. Автосинхронизации пользователей нет.
Самостоятельный scouting_server не вызывает `FieldStore.init()` и не создаёт
яблоневый профиль/измерения/прогнозы из старого погодного пилота.

## Локальный токен, HTTP и ошибки

После старта сервера `GET /state` даёт `token`; все POST передают
`Content-Type: application/json` и `X-Field-Token: <runtime token>`. Токен общий
для этого локального процесса и меняется после рестарта. Это не пользовательская
учётная запись, не JWT и не полномасштабная многопользовательская авторизация.
Не сохранять его в примерах, Git, URL или черновиках; после рестарта перечитать state.

| Код | Значение для клиента |
|---|---|
| 200 | Успешное чтение или сохранённый event |
| 400 | Неверные ключи, дата/место/версия, подтверждение, конфликт retry, невалидное фото и т.п.; JSON `{error:string}` |
| 403 | Чужой Host/Origin либо отсутствующий/старый токен записи |
| 404 | Неизвестный маршрут или POST-действие |
| 503 | Отсутствуют файлы архива или ошибка доступа к локальным файлам/журналу |

Отсутствующий фото-ID существующего маршрута может вернуться как 400 через общий
обработчик KeyError, а не 404. Не предполагать отдельные машинные error-коды или
422/409/413: в этом сервере они не реализованы. Текст ошибки не парсить как схему.
JSON синтаксически неверного POST также попадает в 400. PATCH/PUT/DELETE обработчика
нет; стандартный HTTP server может ответить 501.

Лимит тела — 100 000 байт для задачи/плана, 21 000 000 для посещения. Query в POST
запрещён. Все ответы `Cache-Control:no-store`, `nosniff`, `Cross-Origin-Resource-Policy:
same-origin`; CSP разрешает только собственные скрипты/стили/соединения и собственные,
data/blob-изображения, запрещает встраивание страницы в iframe.

Сервер слушает **127.0.0.1**. Разрешены точные Host `127.0.0.1:port` / `localhost:port`
и соответствующие Origin. Отсутствующий Origin сам по себе не запрещён, но Host
и токен для записи всё равно проверяются. Не открывать сервер на `0.0.0.0`, не
добавлять wildcard CORS и не ослаблять CSP ради нового дизайна.

Рекомендуемый dev-путь — существующий сервер на отдельном порту и отдельном журнале:

```powershell
.\START_SCOUTING.cmd --port 8776 --directory data/frontend-dev-journal
```

Если новый фронтенд работает отдельным dev-сервером, запросы браузера должны идти
на его **same-origin** `/api/...`, затем через ограниченный loopback reverse proxy
к backend. Прокси обязан согласовать точные Host/Origin с upstream; простого
`changeOrigin` только для Host может не хватить. Токен получать у того же backend,
API, PNG и фото проксировать согласованно. Не превращать это в публичный API-прокси.
Не отключать защиту backend при 403. Новая система сборки/HMR и её CSP-интеграция
здесь пока не реализованы; согласовать изменение сервера отдельно.

## Минимальная проверка после UI-изменения

1. `/state` оставляет пустой тестовый журнал пустым.
2. Площадь без пары/облачное окно показываются без подставленных чисел.
3. Пара/место/версия сохраняются именно из текущего выбора, в том числе после
   быстрого переключения и запоздавших ответов сети.
4. Двойной клик/повтор запроса не создаёт вторую задачу.
5. Осмотр нельзя сохранить без фактического ввода/подтверждения; предпросмотр не пишет.
