## Реализованные интерфейсы

| Запрос | Назначение |
|---|---|
| `GET /api/scouting/state` | Площади, периоды, версия архива, задачи/посещения/планы, локальный токен сохранения |
| `GET /api/scouting/workspace?period=…` | Общая пара дат и сравнение всех площадей; для явной пары одновременно передать `before` и `after` |
| `GET /api/scouting/area?fid=…&period=…&before=…&after=…` | Подробности площади на этой паре, доступные даты, качество, опорное место |
| `GET /api/scouting/map?fid=…&period=…&before=…&after=…&key=…&side=…` | PNG на одной сетке; key=`ndvi`/`ndmi`, side=`before`/`after`/`delta` |
| `GET /api/scouting/location?fid=…&period=…&before=…&after=…&relative=…` | Проверка выбранной относительной точки и привязка окна 60 м; relative — JSON `[x,y]` |
| `POST /api/scouting/tasks` | Сохранение вопроса вместе с выбранным местом и исходным основанием |
| `GET /api/scouting/history?place_id=…` | История спутниковых индексов одного фиксированного окна |
| `POST /api/scouting/visits` | Отдельная фактическая запись автора после настоящего осмотра |
| `POST /api/scouting/plans` | План из сохранённых задач, до трёх разных мест |
| `GET /api/scouting/plans/export?id=…` | Сохранённый план и полное основание его задач |
| `GET /api/scouting/export` | Выгрузка задач/посещений; это не автоматически размеченный обучающий датасет |

Все POST используют JSON и `X-Field-Token`, полученный из state. Токен не сохранять
в Git, примерах или документации. `request_id` — отдельный идемпотентный ID формы;
после сбоя повтор того же тела использует тот же ID. Изменённое тело с прежним ID
отклоняется, что защищает исходные записи от перезаписи.

Точный существующий формат POST смотреть в `web/scouting/app.js` и `plans.js`;
серверные проверки — `farm_scouting.py` и `farm_workspace.py`. Структуры не заменять
на выдуманный экспорт АгроМон. Результаты, диагнозы, фото и обучающие метки не
создаются при открытии карты или просмотре пустой формы.

Для идентификатора задачи использовать возвращённый `task.id`; для истории места —
канонический `payload.place.id`. R01–R27 — коды реконструкции, не реальные номера
полей АгроМон. Новые контуры/ID будут сопоставляться отдельно с происхождением.

## Что интерфейс должен различать

- Поле/фрагмент и конкретное окно 60 × 60 м.
- Дату съёмки, дату получения и дату выдачи модели.
- Отсутствие данных, отсутствие изменения и отсутствие подтверждения осмотра.
- Покрытие общими пикселями и точность модели.
- Наблюдаемое снижение, прогноз будущего индекса, рекомендацию осмотра и фактическую
  запись агронома. Эти четыре вида результата не объединяются в одну «тревогу».
- Ретроспективный архив и новый теневой выпуск; один не переименовывается в другой.

Шкалы/маски PNG, отношение сторон и координаты клика должны оставаться согласованы.
Пространственные расчёты, пороги, конверсию единиц, сортировку научных рейтингов и
заполнение облачных пропусков фронтенд самостоятельно не добавляет.

## Проект модельного контракта

Планируем отдельный read-only маршрут, например
`GET /api/model/v1/inspection-priorities?as_of=…`; **сейчас такого маршрута нет**.
До реализации и проверки используйте только существующий API архива. Статический
[пустой пример](priority-response-draft.json) обозначает недостаточность данных,
а не результаты работы модели. Синтетических осмотров и чисел вероятности в нём нет.

Предлагаемая единица ответа:

- `schema_version`, `status`: `insufficient_data` / `archive_review` / `shadow_review`.
- `as_of_utc`, `generated_at_utc`, `data_version`, `model_version`, `target`.
- `field_reference`: источник ID/геометрии и флаг подтверждения.
- `quality`: последний пригодный момент, возраст, покрытие, версия обработки,
  пропуски/причины отказа. Не заменять неизвестные значения нулями.
- `recommendations[]`: каноническое место, вопрос, сравнительный приоритет,
  исходные даты/метрики, объяснение и ссылки на источники.
- `validation`: статус проверки именно этого target, пригодный знаменатель,
  сравниваемая база, проверочные периоды, дата заморозки. Без допустимой проверки
  `probability_useful=null`; score не превращается в вероятность.

Названия и типы фиксируются перед реализацией сервиса, затем версия повышается при
несовместимом изменении. Фронтенд может менять расположение и внешний вид этих
сведений, сохраняя смысл и серверные ограничения. Расчёт модели не зависит от дизайна.

## Приёмка интеграции к 2–3 декабря

Одинаковые место/даты/версия проходят весь путь: карта → основание → задача →
посещение → история. Работают пустые/облачные/устаревшие случаи, ошибка сети,
повтор сохранения, отсутствие доступа и восстановление черновика. Демонстрация
не создаёт фактического посещения. Проверка расчётов и пользовательский тест
агрономом отражаются отдельно от визуальной приёмки.
