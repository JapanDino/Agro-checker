## Запуск с нового ноутбука

Нужны Git и **Python 3.13 x64**. Для существующего интерфейса Node и сборщик не нужны.

```powershell
git clone --branch J-D/frontend-handoff-dec04-2026 --single-branch https://github.com/JapanDino/Agro-checker.git
cd Agro-checker
.\START_SCOUTING.cmd --port 8776 --directory data/frontend-dev-journal
```

Открыть <http://127.0.0.1:8776/scouting>. Окно сервера оставить открытым;
остановка — Ctrl+C. Первый запуск устанавливает зафиксированные зависимости из
интернета и проверяет 92 включённых архива индексов. Необходимые для `/scouting`
сырые многогигабайтные TIFF не требуются. Рабочий журнал разработчика начинается
пустым и исключён из Git. Личные записи команды при клонировании не передаются.

Если репозиторий уже клонирован, сначала сохраните свои изменения:

```powershell
git fetch origin
git switch --track origin/J-D/frontend-handoff-dec04-2026
.\START_SCOUTING.cmd --port 8776 --directory data/frontend-dev-journal
```

Если эта локальная ветка уже существует: `git switch J-D/frontend-handoff-dec04-2026`.
Для следующих обновлений остановить сервер, выполнить `git pull --ff-only` и
запустить снова. При занятом порте выбрать другой.

## Что проверить первым

1. Открывается карта 27 рабочих обводок; журнал посещений пуст.
2. Кнопка **«Архивный пример»** открывает R11, 21 сентября → 14 октября 2026 года.
3. Открывается сравнение; можно выбрать место внутри обводки и сформулировать задачу.
4. После сохранения задачи открывается история именно этого места.
5. **«Посмотреть форму без записи»** показывает результат без фиктивного посещения.
6. Задача включается в необязательный план выезда; доступны печать и выгрузки.
7. Переключатель «Хай-тек / Атлас» сохраняет контекст.

Задачу для проверки создавать только в отдельном журнале разработчика. Реальное
посещение не имитировать в журнале хозяйства. Архивный пример не означает текущую
проблему на поле. [Полный сценарий показа](../DEFENSE_WALKTHROUGH.md).

## Стек и точки входа

| Слой | Где работать | Ответственность |
|---|---|---|
| Структура экранов | `web/scouting/index.html`, `about.html` | Карта, анализ, задача, история, выезды |
| Поведение | `web/scouting/app.js` | Выбранная площадь/даты/место, формы, загрузка API |
| Карта | `web/scouting/map.js` | Leaflet, слои, выделение, координаты клика |
| Выезды | `web/scouting/plans.js` | Задачи в плане, печать, JSON/GeoJSON |
| Черновики | `web/scouting/drafts.js` | Контекстные ключи, восстановление, защита от дублей |
| Оформление | `web/scouting/hightech.css`, `design.js`, `design-controls.css` | Независимая тема, переключение и сохранение предпочтения |
| Прежнее оформление | Пять CSS с `data-design-sheet="atlas"` в HTML | Сохраняемый вариант отката |
| Локальный HTTP | `agro_checker/scouting_server.py` | Точные маршруты, локальный доступ, JSON/PNG/фото |
| Архив и журнал | `agro_checker/farm_scouting.py`, `farm_workspace.py` | Научный смысл, каноническое место, задачи/осмотры/планы |
| Модельная работа | `agro_checker/`, `scripts/`, `config/`, отчёты | Отдельная ветка `J-D/model-pilot-dec04-2026` |

Фронтенд сейчас — обычные HTML/CSS/JavaScript с локальной Leaflet 1.9.4.
Сервер — Python и SQLite; вычисления используют NumPy и геопространственные
библиотеки. Требования зафиксированы в `requirements-scouting-lock.txt`.

Разработчик может предложить другой фронтенд-стек, но миграция должна сохранить
весь сценарий, форматы данных, геопривязку, защиту журнала и простой запуск.
Это отдельная задача с оценкой сроков, а не обязательная часть редизайна.

## API и граница работы

[Реализованные маршруты и правила запросов](../pilot-dec04/FRONTEND_HANDOFF.md)
проверены по серверу. Примеры формирования POST находятся в `app.js` и `plans.js`.
Поля тела проверяются сервером строго: произвольные новые поля не принимаются.

- Использовать относительные `/api/scouting/...`; изображения PNG и фото брать
  из того же источника. Собственный dev-сервер подключать через прокси.
- Для POST получать `X-Field-Token` из `/api/scouting/state`; токен не коммитить.
- У задачи использовать возвращённый `task.id`; у места — `task.payload.place.id`.
  API выбора точки возвращает `location.id`. Не создавать новый ID места в браузере.
- Повтор неизменённого запроса после сетевого сбоя использует прежний `request_id`;
  для нового содержания нужен новый ID. Не превращать повтор клика в две записи.
- Архивная версия, исходная пара, маски и единицы остаются серверными.
- Не ослаблять Origin/Host и не добавлять wildcard CORS ради удобства разработки.

**Будущий `/api/model/v1/inspection-priorities` не реализован.**
[JSON-проект](../pilot-dec04/priority-response-draft.json) — только обсуждение
контракта, не выдача работающей модели. Исследовательский score не отображать как
вероятность болезни или полезного осмотра.

Общие изменения сервера/API согласовываются отдельным коммитом: обе ветки уже
имеют одну исходную точку. Не переносить ветку модели целиком поверх UI и не
перезаписывать `data/` при слиянии. Секреты, фотографии и журналы не входят в Git.
